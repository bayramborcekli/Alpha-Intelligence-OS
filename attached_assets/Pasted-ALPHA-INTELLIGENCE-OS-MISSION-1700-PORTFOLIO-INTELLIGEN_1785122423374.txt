4. API CONTRACT

Expose one read-only endpoint using the repository’s established API style.

Recommended route:

GET /api/portfolio/intelligence

Use the exact route prefix and registration pattern already established in
the repository when a different canonical convention exists.

The endpoint must:

• accept no execution instructions

• accept no order parameters

• accept no mutable portfolio commands

• invoke get_portfolio_analysis(...) or PortfolioService.get_analysis(...)

• return the Service result without reimplementing calculations

• use the application’s existing JSON response mechanism

• preserve null values

• preserve analysis_version

• preserve read_only: true

• preserve advisory_only: true

6. DEPENDENCY INTEGRATION

The API must depend on the Service Layer, not directly on Core calculations.

Allowed flow:

HTTP API
↓
Portfolio Service
↓
Portfolio Core
↓

Disallowed flow:

HTTP API
↓
portfolio calculations

The API may construct or receive the approved default read-only providers
through existing dependency wiring.

Do not embed provider logic in the route.

Do not access Intelligence Engine, Risk Engine or Exchange directly from the
route when the Service already owns that integration.

────────────────────────────────────────
7. GENERATED_AT

The Core and Service do not read wall-clock time.

The API must follow the approved application boundary for generated_at.

Use one of these approaches, according to existing repository conventions:

• inject generated_at through an approved request-independent clock dependency

or

• accept a server-generated timestamp at the API composition boundary

Requirements:

• no timestamp calculation inside Core

• no timestamp calculation inside Service

• deterministic tests must inject a fixed generated_at

• generated_at must not be accepted as an untrusted client override unless
  the existing API architecture explicitly supports and validates it

Do not change the approved Core or Service contracts.

────────────────────────────────────────
9. HTTP STATUS MODEL

Use deterministic, documented status mapping consistent with existing API
conventions.

Portfolio availability states are domain states and should remain represented
inside the response envelope.

Preferred behavior unless repository conventions require otherwise:

• OK → HTTP 200

• PARTIAL → HTTP 200

• UNAVAILABLE → HTTP 200 with domain status UNAVAILABLE

Unexpected API composition failures may use a sterile server error response.

Do not expose exception text or traceback.

Do not convert advisory unavailability into a fake successful portfolio.

Do not expose:

• traceback content

• filesystem paths

• credentials

• provider internals

• Risk Engine internals

• Exchange internals

Use stable error codes consistent with repository conventions.

Unexpected exceptions must be caught at the appropriate API boundary without
changing Service or Core semantics.

Do not swallow valid PortfolioAnalysis envelopes.
