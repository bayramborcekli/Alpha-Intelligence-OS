3. API KAPSAMI

Repository mimarisine uygunsa en az aşağıdaki yüzeyleri oluştur:

A. Durum sorgulama

GET /api/automation/status

Amaç:

• enabled
• current state
• last run
• next due
• last result code
• running durumu

gibi sterile ve read-only bilgileri döndürmek.

B. Manuel tetikleme

POST /api/automation/run

Amaç:

• tek kontrollü automation çalışması başlatmak,
• duplicate run durumunda güvenli cevap vermek,
• hata ayrıntısı veya exception metni sızdırmamak.

C. Etkinleştirme / devre dışı bırakma

Yalnız mevcut mimari gerçekten destekliyorsa:

POST /api/automation/enable
POST /api/automation/disable

Bu uçlar runtime güvenliği ve kalıcı yapılandırma modeliyle uyumlu değilse
eklenmeyecek ve BLOCKED/OUT OF SCOPE olarak raporlanacaktır.

Kanıtsız endpoint ekleme.

────────────────────────────────────────
4. AUTHENTICATION / AUTHORIZATION

Tüm management endpoint'leri mevcut auth modelini kullanmalıdır.

Zorunlu kurallar:

• anonim kullanıcı erişemez,
• yalnız uygun yetkiye sahip kullanıcı manuel tetikleyebilir,
• durum endpoint'i dahi mevcut authorization politikasına uymalıdır,
• yeni ve paralel auth sistemi oluşturulmayacaktır,
• role/permission isimleri repository'deki mevcut sözleşmeden alınacaktır.

Yetki modeli kanıtlanamıyorsa yeni rol icat etme.

────────────────────────────────────────
5. CSRF

Durum değiştiren tüm POST uçları mevcut CSRF mekanizmasıyla korunmalıdır.

Yasak:

• CSRF bypass
• özel istisna
• yalnız API olduğu gerekçesiyle korumayı kaldırma
• token'ı query string ile kabul etme

Mevcut sistem JSON endpoint'leri için farklı, kanıtlı bir güvenlik deseni
kullanıyorsa onu uygula ve raporla.

────────────────────────────────────────
6. RESPONSE SÖZLEŞMESİ

API cevapları:

• deterministik,
• sterile,
• minimum alanlı,
• secret içermeyen,
• path/traceback/exception metni içermeyen

yapıda olmalıdır.

Örnek durum kodları repository sözleşmesine göre seçilmelidir:

• 200 — başarılı sorgu veya kabul edilen senkron işlem
• 202 — asenkron kabul, gerçekten asenkron model varsa
• 400 — geçersiz istek
• 401 — kimlik doğrulama yok
• 403 — yetki veya CSRF reddi
• 409 — duplicate/running conflict
• 503 — servis devre dışı veya kullanılamıyor

Mevcut API standardı farklıysa mevcut standardı koru.

8. APPLICATION LIFECYCLE / SCHEDULER BAĞLANTISI

Agent 01 kararı ve repository'deki kanıtlı uygulama modeli uygulanacaktır.

İncelenecekler:

• Gunicorn kullanılıyor mu?
• post_fork hook mevcut mu?
• app factory var mı?
• debug reloader duplicate thread riski var mı?
• her worker'da scheduler çalışması isteniyor mu?
• tek global scheduler garantisi gerçekten mümkün mü?

Zorunlu davranış:

• Automation varsayılan olarak kapalı kalmalıdır.
• Yalnız enabled literal true ise scheduler başlatılmalıdır.
• Aynı process içinde birden fazla loop başlatılmamalıdır.
• Scheduler thread'i daemon ve stop_event kontrollü olmalıdır.
• Startup hatası uygulamayı çökertmemelidir.
• Exception ayrıntısı secret veya response yüzeyine taşınmamalıdır.
• Lock mekanizması duplicate execution'ı yine Core seviyesinde önlemelidir.

Her worker'da loop başlatma mimarisi varsa bunu açıkça raporla.
Dağıtık tek-scheduler garantisini kanıtsız iddia etme.
