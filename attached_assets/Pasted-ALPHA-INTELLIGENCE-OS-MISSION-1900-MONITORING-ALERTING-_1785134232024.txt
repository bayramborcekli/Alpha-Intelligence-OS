2. OBJECTIVE

Implement a thin orchestration service that:

• Retrieves Monitoring observations from providers

• Calls Monitoring Core exactly once

• Calls Alert Engine exactly once

• Returns one immutable MonitoringAnalysis envelope

The Service SHALL own orchestration only.

The Service SHALL NOT own:

• Metric calculations

• Health calculations

• Alert rule evaluation

• Serialization

• API metadata

4. PROVIDER MODEL

Implement deterministic provider orchestration.

Suggested provider interface:

MonitoringProvider

get_monitoring_input()

returns:

MonitoringObservationInput

The default provider chain SHALL remain read-only.

No provider may:

• Persist observations

• Modify Monitoring Core output

• Generate alerts

• Access Exchange write APIs

7. SOURCE REPORTING

sources SHALL describe provider execution only.

Allowed values:

COMPLETE

PARTIAL

UNAVAILABLE

UNAVAILABLE

or

PARTIAL

Never raw exceptions.

Never stack traces.

Never secrets.

────────────────────────────────────────
8. PROVIDER FAILURE

Rules:

Provider unavailable

↓

UNAVAILABLE source

↓

Monitoring Core still executes using empty input
when safely possible.

Provider partial

↓

PARTIAL source

↓

Monitoring proceeds.

Unexpected exception

↓

Sterile provider failure

↓

No traceback leakage.
