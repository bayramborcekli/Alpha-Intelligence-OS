6. EXECUTION PERMISSION GATE

Create:

ExecutionPermissionGate

This is the single authority that combines:

RiskDecision

AND

KillSwitch state

The gate SHALL answer:

“May this execution proceed to BrokerAdapter?”

Permission is granted only when:

RiskDecision = ALLOW

AND

KillSwitch.is_execution_allowed() = True

All other combinations SHALL deny broker submission.

Examples:

ALLOW + ENABLED
→ PERMIT

ALLOW + DISABLED
→ DENY

ALLOW + LOCKED
→ DENY

ALLOW + MAINTENANCE
→ DENY

REJECT + ENABLED
→ DENY

REDUCE_SIZE + ENABLED
→ DENY unless a new explicitly approved request has already been created

REQUIRE_CONFIRMATION + ENABLED
→ DENY

The gate SHALL NOT:

• change RiskDecision
• resize an order
• ask for confirmation
• change Kill Switch state
• call BrokerAdapter

────────────────────────────────────────
7. NO IMPLICIT RESIZING

RiskDecisionType.REDUCE_SIZE SHALL NOT cause the Execution Service to silently
change quantity.

Required behavior:

• Return a non-submitted service result
• Include the recommended reduced quantity when available
• Require the caller to create a new explicit ExecutionRequest
• Require a new caller-owned idempotency key for the revised operation

This protects:

• auditability
• user intent
• strategy intent
• idempotency integrity
• deterministic replay

No hidden order mutation.

12. RISK ENGINE INTEGRATION

Execution Service SHALL call the canonical Risk Engine public API.

It SHALL NOT:

• recreate exposure calculations
• recreate capital validation
• inspect risk policies
• infer ALLOW from individual fields
• convert REJECT into ALLOW
• bypass REQUIRE_CONFIRMATION
• silently accept REDUCE_SIZE

RiskDecision is authoritative for risk.

Exactly one risk evaluation per execution attempt.

No hidden re-evaluation after broker submission.

────────────────────────────────────────
13. KILL SWITCH INTEGRATION

Kill Switch SHALL be checked:

• after Risk Engine approval
• immediately before BrokerAdapter write invocation

The check and broker invocation SHALL occur within one explicit orchestration
path.

Execution Service SHALL NOT:

• call enable()
• call disable()
• call lock()
• call maintenance()
• mutate snapshots
• cache an old permission indefinitely
• treat a previous ENABLED result as permanent

For each submission attempt, current Kill Switch permission SHALL be read.

No broker write occurs when Kill Switch denies execution.

────────────────────────────────────────
15. IDEMPOTENCY PROPAGATION

The service SHALL require caller-owned idempotency for state-changing execution.

Rules:

• idempotency_key is mandatory for submission
• service never generates it
• service passes it unchanged into BrokerRequestContext
• broker adapter receives exactly the same key
• rejected pre-broker attempts do not call the adapter
• retry is never automatic
• conflicting request identity is rejected deterministically where detectable
• no hidden replacement key
• no key mutation
• no hashing that changes caller identity

Distributed idempotency storage remains deferred.

────────────────────────────────────────
16. EXACTLY-ONCE CLAIM PROHIBITION

Agent 07 SHALL NOT claim exactly-once execution.

The correct guarantee is:

• one BrokerAdapter invocation per service method call after successful gates
• no internal retry
• no duplicate call within one orchestration attempt
• caller-owned idempotency propagated unchanged

Cross-process exactly-once behavior requires persistence and broker support and
is deferred.

Tests SHALL prevent misleading exactly-once claims in documentation.

• broker resolution fails

• Kill Switch denies execution
• request context is invalid

• BrokerAdapter submit_order is not called
• no side effects occur
• trace ends at the correct denial step
• deterministic service result is returned

Tests SHALL verify adapter invocation count = 0 for every denied path.

30. SINGLE BROKER WRITE RULE

• twice
• inside a retry loop
• from a finally block
• from error recovery
• from trace generation

34. ARCHITECTURAL INVARIANTS

Test-freeze these invariants:

1. There is one canonical execution entry point.

2. Risk Engine is evaluated before Kill Switch.

3. Kill Switch is checked immediately before broker submission.

4. No broker submission occurs without RiskDecision.ALLOW.

5. No broker submission occurs unless Kill Switch permits execution.

6. REDUCE_SIZE never silently modifies the request.

7. REQUIRE_CONFIRMATION never reaches BrokerAdapter.

8. Caller owns idempotency identity.

9. BrokerAdapter is invoked at most once per execute() call.

10. No automatic retry exists.

11. Execution Service contains no broker-specific logic.

12. Execution Service contains no risk-calculation logic.

13. Execution Service cannot modify Kill Switch.

14. Native broker objects cannot cross the boundary.

15. Monitoring remains read-only and independent.

16. Execution Service does not claim distributed atomicity.

17. Execution Service does not claim exactly-once execution.

18. Same inputs and dependency outputs produce the same result and trace.
