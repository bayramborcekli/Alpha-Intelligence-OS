MISSION 1400.2 — READ-ONLY LIVE DASHBOARD

OBJECTIVE

Turn the existing authenticated Alpha Intelligence OS shell into a secure,
read-only live dashboard for Binance Global, Binance Global Futures and
Binance TR.

This sprint must display live account and connection data after owner login.

It must not create, submit, modify or cancel orders.
It must not transfer or withdraw funds.
It must not change leverage, margin mode or position mode.

BASELINE

Mission 1400.1 is complete and closed.

Preserve:

- single-owner authentication
- secure sessions
- CSRF protection
- rate limiting
- request IDs
- Turkish UI
- current application shell
- existing feature flags
- existing Binance clients
- existing deterministic ledger
- existing mission reports
- all 413 passing tests
- current Git history

Current application status:

- setup_state = READY
- owner login works
- PAPER mode active
- live trading disabled
- transfers disabled
- withdrawals disabled
- Binance write routes = 0

Do not redesign or replace the authentication architecture.

PRIMARY GOAL

After login, the owner must see a useful live “Genel Bakış” page showing:

- Binance Global read-only connection
- Binance Global Futures account status
- Binance Global trading-key authentication status
- Binance TR connection
- important balances

All exchange access in this sprint must use explicitly allowlisted GET requests.

Forbidden:

- POST exchange requests
- PUT exchange requests
- PATCH exchange requests
- DELETE exchange requests
- order creation
- order cancellation
- transfer
- withdrawal
- leverage changes
- margin mode changes
- position mode changes

- futures wallet transfer
- automatic trading

Track and report:

- TRANSFER ENDPOINT REQUESTS

- OTHER EXCHANGE WRITE REQUESTS

All must remain zero.

EXISTING /panel ROUTE

Inspect the existing read-only /panel implementation before changing anything.

There must be only one primary dashboard experience.

Choose one safe approach:

A. Integrate useful /panel functionality into the authenticated application shell,
then redirect /panel to /overview.

or

B. Reuse /panel as the implementation behind the new Genel Bakış page while
preserving the current shell.

Do not leave two independent dashboards with different data or security rules.

Do not remove a working route without a compatibility redirect.

BACKEND ROUTES

Implement authenticated, versioned, typed routes:

- GET /api/v1/overview
- GET /api/v1/global/account
- GET /api/v1/global/positions
- GET /api/v1/global/orders
- GET /api/v1/tr/account
- GET /api/v1/tr/movements/summary
- GET /api/v1/system/status
- POST /api/v1/refresh

The refresh route is an application-local authenticated action only.

It may:

- invalidate safe read caches
- initiate fresh server-side GET requests
- record an audit event

It must not call any exchange write endpoint.

Keep existing:

- GET /api/v1/health
- GET /api/v1/application/config
- authentication routes

All new routes require a valid owner session.

CSRF-protect POST /api/v1/refresh.

Do not expose raw exchange payloads directly.

Create stable response models.

Suggested common metadata:

{
  "source": "BINANCE_GLOBAL",

  "age_seconds": "decimal/integer",
  "freshness": "FRESH | STALE | UNAVAILABLE",
  "latency_ms": "integer",

Use Decimal-compatible serialization for financial values.

Do not calculate balances with binary float.

DATA FRESHNESS

Every exchange-derived component must display:

- source
- retrieval timestamp
- age
- status:
  - GÜNCEL
  - ESKİ VERİ
  - KULLANILAMIYOR

Suggested thresholds:

Market or mark price:
- fresh: 0–10 seconds
- stale: over 10 seconds

Account, balances, positions and orders:
- fresh: 0–60 seconds
- stale: over 60 seconds

Binance TR movement history:
- fresh: 0–15 minutes
- stale: over 15 minutes

Use a centralized freshness policy.

Never label unavailable or stale data as live.

CACHING

Implement small, server-side read caches to reduce exchange rate-limit risk.

Requirements:

- cache only sanitized read models or safe raw data held server-side
- never cache secrets
- separate cache keys per source
- visible retrieved timestamps
- manual refresh invalidates only relevant safe caches
- safe GET retry only
- bounded retry count
- exponential or controlled backoff
- no retries for future write operations
- fail safely when rate-limited

Suggested cache TTL:

- overview/account: 15 seconds
- positions/orders: 10 seconds
- Binance TR account: 30 seconds
- movement summary: 5 minutes

Do not hide cached-data age.

ERROR HANDLING

Normalize safe errors:

- EXCHANGE_AUTH_FAILED
- EXCHANGE_UNAVAILABLE
- EXCHANGE_RATE_LIMITED
- EXCHANGE_TIMEOUT
- INVALID_EXCHANGE_RESPONSE
- STALE_DATA
- APPLICATION_LOCKED
- UNAUTHORIZED
- CSRF_FAILED

UI messages must be Turkish and user-friendly.

Do not show raw exchange messages unless safely mapped.
